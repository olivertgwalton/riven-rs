# Migrating auth from the TypeScript frontend

Riven used to keep its users in the SvelteKit frontend's own SQLite database,
managed by the TypeScript `better-auth` package. Authentication now lives in the
backend (`crates/riven-api/src/server/authn.rs`), with the tables created by
migration `m036`.

Existing users port across by copying rows — no re-registration, and everyone
keeps their password. **Password hashes carry over as-is**: they are scrypt in
the TypeScript library's format, and `DualFormatHasher`
(`crates/riven-api/src/server/legacy_password.rs`) verifies both that and the
Argon2 it writes for new passwords. It is pinned against a vector generated by
the TypeScript library itself, so a migrated user signing in is covered by a
test.

## This is a manual, one-off step

There is deliberately no import file in `crates/riven-db/migrations/`. Anything
there runs automatically on every instance, and an auth import is inherently
specific to one deployment — it would carry real email addresses, usernames and
password hashes. Generate the SQL locally, run it once, and do not commit it.

Sessions and verification rows are deliberately *not* imported: sessions are
short-lived and cookie-scoped to the old origin, so everyone signs in once more
after the cutover, and verification rows are expiring tokens with no value
afterwards.

## Generating the import

Read the frontend's SQLite database and emit one `INSERT` per row into the
`auth_users` and `auth_accounts` tables. The shape, with every value a
placeholder:

```sql
BEGIN;

INSERT INTO auth_users (
    id, name, email, email_verified, image,
    created_at, updated_at,
    username, display_username, role,
    banned, ban_reason, ban_expires
) VALUES (
    '<user-id>', '<display name>', '<email>', false, NULL,
    '<created-at>', '<updated-at>',
    '<username>', NULL, 'admin',
    false, NULL, NULL
) ON CONFLICT (id) DO NOTHING;

INSERT INTO auth_accounts (
    id, account_id, provider_id, user_id,
    access_token, refresh_token, id_token,
    access_token_expires_at, refresh_token_expires_at, scope,
    password, created_at, updated_at
) VALUES (
    '<account-id>', '<user-id>', 'credential', '<user-id>',
    NULL, NULL, NULL,
    NULL, NULL, NULL,
    '<scrypt-salt-hex>:<scrypt-key-hex>', '<created-at>', '<updated-at>'
) ON CONFLICT (id) DO NOTHING;

COMMIT;
```

Notes on the columns that matter:

- `provider_id` is `'credential'` for password accounts, `'plex'` for a linked
  Plex identity. Keep the original value so an existing Plex link survives.
- `password` is the scrypt hash exactly as the frontend stored it —
  `salt_hex:key_hex`, 32 and 128 hex characters respectively.
- `role` maps onto riven's ladder: `admin`, `manager`, or `user`. Anything
  unrecognised is read as `user`, the least privilege.
- `ON CONFLICT (id) DO NOTHING` keeps the script idempotent, so a partial run is
  safe to repeat.

## Applying it

After the schema migrations have run and created the tables:

```sh
psql "$RIVEN_SETTING__DATABASE_URL" -f /path/to/your/import.sql
```

Delete the file afterwards. It contains password hashes, so treat it like any
other credential material: keep it out of version control, and off shared
storage.

## If you are starting fresh

You do not need any of this. Open the UI and create an account — the first one
becomes the admin, and sign-up closes permanently after it.
